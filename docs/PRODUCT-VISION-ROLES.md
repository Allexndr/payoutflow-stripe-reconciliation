# Продукт: сверка, зрелость, роли и тарифы

Документ фиксирует **зачем** сделан PayoutFlow, **что уже есть**, **чего не хватает** для «полной» сверки как в зрелых продуктах, и **модель аккаунтов/ролей** для дальнейшей реализации.

---

## 1. Три слоя продукта

| Слой | Назначение | Сейчас |
|------|------------|--------|
| **Маркетинг** | Лендинг, доверие, вход / регистрация | Есть (`/`, `/login`, `/register`) |
| **Платформа (SaaS)** | Настройки, биллинг, интеграции, пользователь | Есть: Settings, Stripe Billing, Connect, Plaid, CSV |
| **Ядро — сверка** | Payout ↔ банк ↔ breakdown из Stripe | Есть базово: список, деталка, матчинг, экспорт, алерты Pro |

**Главная ценность продукта** — не лендинг, а **сверка**: понять, что пришло в банк относительно payout Stripe и из чего он сложен. Остальное — обвязка (доступ, оплата, подключения).

---

## 2. Что уже закрывает «сверку» в MVP

- Данные payout + balance transactions в кэше, матчинг с банком (Plaid / CSV).
- Статусы Matched / Review, % расхождения, Pro-алерты по порогу.
- Экспорт CSV, ручной sync, webhooks на payout.

---

## 3. Чего не хватает до «максимального удобства» (типичный backlog класса reconciliation)

Ниже — не обязательно всё делать; это **карта зрелости**, как в Stripe Treasury / бух-платформах / internal tools.

### 3.1 Объём данных и производительность

| Функция | Зачем |
|---------|--------|
| Пагинация / виртуализация списка payout | Много строк без подвисаний (**сделано:** `PayoutTableToolbar` + `listPayoutRowsForUser`) |
| Пагинация breakdown (>100 balance txns) | ТЗ §4 |
| Фильтры: дата, сумма, статус, валюта | Быстро найти проблемный payout (**сделано:** `match`/`from`/`to`/`min`/`max`/`q` на дашборде и в экспорте) |
| Поиск по ID / memo | Операционка (**сделано** по payout id; memo — позже) |
| Строгий лимит Free «N payout за календарный месяц» | Совпадение с ТЗ §3.7 (сейчас — только 5 строк в списке) |

### 3.2 Качество сверки

| Функция | Зачем |
|---------|--------|
| Ручное подтверждение match / выбор другого кандидата | Когда алгоритм «Review» или ошибся (**сделано:** `ManualMatchPanel` + `payout_matches`) |
| AI-объяснение Review и next actions | Снижает время ручного анализа (**сделано:** блок AI insight на payout detail) |
| Комментарии к payout | Журнал бухгалтерии (**сделано:** `CommentsPanel` + `payout_comments`) |
| Аудит-лог действий | Основа SOC2 (**сделано:** `payout_events` + блок Activity на detail) |
| Правила матчинга (окно дней, %, счета) per org | Разные банки и процессы |
| Несколько банковских счетов / Items Plaid | Реальный SMB часто не один счёт |
| Исключения / корректировки (adjustment) | Ручные проводки вне Stripe |

### 3.3 Операции и аудит

| Функция | Зачем |
|---------|--------|
| История изменений (кто подтвердил сверку) | SOC2 / внутренний контроль (**сделано:** `payout_events`) |
| Комментарии к payout | Совместная работа (**сделано:** `payout_comments` + `CommentsPanel`) |
| Экспорт с фильтрами «как на экране» | **сделано:** `/api/payouts/export` принимает `match/from/to/min/max/q` |
| Закрытие периода (month-end lock) | Бухгалтерия |

### 3.4 Интеграции (вне MVP по ТЗ)

- Другие процессоры: PayPal, Shopify, Adyen.
- Уведомления: Slack, не только email.
- API / webhooks наружу для ERP.

### 3.5 Надёжность

- Очередь для тяжёлых sync (Inngest/QStash) — в ТЗ как опционально.
- Автотесты матчинга и E2E — в ТЗ §6.

## 4. Две оси: тариф (биллинг) и роль (доступ)

Их **нельзя смешивать** в одну кнопку:

- **Тариф** (Free / Pro / Scale) — сколько данных, алерты, поддержка, будущие лимиты API.
- **Роль** — что пользователь **может делать** внутри организации (читать, менять интеграции, подтверждать сверку).

Сейчас в коде есть только **тариф** на пользователе (`sub_tier`). **Ролей и организаций нет** — один пользователь = один аккаунт = один набор Connect/Plaid.

---

## 5. Модель аккаунтов и ролей (целевая)

### 5.1 Организация (Workspace)

- Сущность **Organization** (компания): к ней привязаны Stripe Connect, Plaid, данные сверки, биллинг (или биллинг остаётся на владельце — продуктовое решение).
- Пользователи состоят в org через **Membership**.

### 5.2 Роли (RBAC)

| Роль | Код | Типичный пользователь |
|------|-----|------------------------|
| **Владелец** | `owner` | Основатель, платит подписку, полный доступ |
| **Администратор** | `admin` | Финдир / IT: интеграции, пользователи, без биллинга (опционально) |
| **Финансы** | `finance` | Сверка: просмотр, экспорт, ручное подтверждение match, комментарии |
| **Наблюдатель** | `viewer` | Только просмотр дашборда и отчётов |
| **Бухгалтер (внешний)** | `accountant` | Узкий доступ: экспорт и просмотр без настроек интеграций (опционально) |

### 5.3 Матрица прав (черновик)

| Действие | owner | admin | finance | viewer | accountant |
|----------|-------|-------|---------|--------|------------|
| Просмотр payout / деталок | ✓ | ✓ | ✓ | ✓ | ✓ |
| Экспорт CSV | ✓ | ✓ | ✓ | ✓* | ✓ |
| Sync Stripe / Plaid | ✓ | ✓ | ✓ | — | — |
| Подключить Stripe / Plaid | ✓ | ✓ | — | — | — |
| Биллинг / план | ✓ | опц. | — | — | — |
| Пригласить пользователя | ✓ | ✓ | — | — | — |
| Ручное подтверждение match (будущее) | ✓ | ✓ | ✓ | — | опц. |
| Удалить org / данные | ✓ | — | — | — | — |

\*Viewer — можно ограничить «только просмотр» без экспорта в минимальном тарифе (политика продукта).

### 5.4 Связь с тарифами

| Тариф | Роли | Заметки |
|-------|------|---------|
| **Free** | 1 пользователь, фактически owner-only | Как сейчас |
| **Pro** | Несколько пользователей, роли finance + viewer | Нужна модель org + invite |
| **Scale** | То же + приоритет, опционально SSO / audit log | Как в ТЗ «командные фичи позже» |

## 6. Рекомендуемый порядок внедрения

1. **Продуктовая сверка без ролей:** фильтры, пагинация, ручной resolve match, тесты `match.ts`.
2. **Организации:** таблицы `organizations`, `memberships`, перенос `stripe_account_id` и данных на `org_id`.
3. **Приглашения и роли:** email invite, проверки в API и RLS/запросах по `org_id`.
4. **Scale-фичи:** аудит, SSO — по запросу рынка.

---

## 7. Сводка: что «осталось по сайту»

- **Сайт (маркетинг)** — можно усиливать кейсы, демо, SEO; ядро уже есть.
- **Платформа** — биллинг и интеграции есть; не хватает **командности** (org + роли) и части **операционного UX** (фильтры, пагинация, ручной match).
- **Сверка** — логика ядра есть; не хватает **масштаба** (объём данных) и **гибкости** (правила, мульти-счёт, аудит).
